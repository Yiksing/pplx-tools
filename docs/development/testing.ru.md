# Тестирование

Набор тестов находится в `tests/`, вне пакета `pplx_export`, и выполняется
полностью в офлайн-режиме. Его входные данные в формате API представляют собой детерминированные симулированные данные, зафиксированные
в `tests/fixtures/`; тесты не зависят от живых сервисов или реальной
конфигурации пользователя.

Эта страница содержит текущий перечень тестовых модулей и рабочий процесс для участников.
Описание регрессионного дизайна см. в разделе
[Архитектура системы тестирования](testing-architecture.md). Описание контракта входных данных см. в разделе [Тестовые фикстуры](fixtures.md).

<a id="running-the-tests" data-pplx-source-anchor="true"></a>
## Запуск тестов

```bash
uv run pytest tests
```

pytest является объявленной зависимостью разработки. Набор тестов гарантирует:

- **Нулевое сетевое взаимодействие** — симулированные входные данные включены в репозиторий; пути, связанные с сетью, покрыты
  с помощью заглушек, `tmp_path` и `monkeypatch`.
- **Отсутствие реальной конфигурации пользователя** — перед импортом любого производственного модуля
  `tests/conftest.py` создает временную конфигурацию в рамках процесса и переопределяет
  `PPLX_EXPORT_CONFIG`. Затем каждый тест получает свою собственную конфигурацию-заполнитель
  `alice` / `bob` и восстанавливает конфигурацию-заполнитель процесса
  после завершения. Регрессионные тесты подпроцессов проверяют, что отсутствующая или поврежденная конфигурация вызывающего
  кода не может нарушить сбор тестов.
- **Быстрая обратная связь** — по состоянию на 2026-07-25 проект наблюдал 435 тестов, собранных
  из 32 модулей `test_*.py`, и полный набор выполнялся примерно за 13–25 секунд
  в различных локальных проверках.
  Количество — это снимок репозитория на определенную дату, и оно будет расти.

Полезные выборки:

| Команда | Эффект |
|---|---|
| `uv run pytest tests` | полный набор |
| `uv run pytest tests/test_units.py` | один модуль |
| `uv run pytest tests -k snapshot` | тесты, идентификатор узла которых соответствует `snapshot` |
| `uv run pytest tests -x -q` | остановка при первой ошибке, тихий вывод |
| `uv run pytest --collect-only -q` | обновление количества собранных случаев |

### Происхождение регрессий по рецензиям

Идентификаторы рецензий объясняют, почему существует регрессия; они не являются
основной архитектурой набора тестов. Сопоставление намеренно «многие ко многим»: один
модуль может охватывать несколько замечаний, а замечание также может добавлять случаи в
существующий тематический модуль.

| Происхождение | Выделенные модули |
|---|---|
| Рецензия N | `test_fix_n01_inline_assets.py`, `test_fix_n02_spaces_link.py`, `test_fix_n03_n12.py`, `test_fix_n04_cookies.py`, `test_fix_n05_n06_n09.py`, `test_fix_n07_usage_checkpoint.py`, `test_fix_n08_throttle_overflow.py`, `test_fix_n10_table_header.py`, `test_fix_n11_batch_total.py` |
| Рецензия V3 | `test_fix_v301_nested_sources_text.py`, `test_fix_v305_export_products.py` |
| Рецензия V4 | `test_fix_v401_thread_dir_migration.py`, `test_fix_v402_manifest_count.py`, `test_fix_v403_handle_assets_idempotency.py`, `test_fix_v405_ask_post_steps.py` |
| Рецензия V5 | `test_fix_v5_review.py`, а также целевые дополнения к существующим тематическим модулям |

Строки документации модулей остаются авторитетным объяснением старого поведения каждого замечания,
исправленного поведения и границы регрессии.

<a id="how-snapshot-tests-reuse-the-production-re-render-path" data-pplx-source-anchor="true"></a>
## Как снимковые тесты используют производственный путь повторного рендеринга

Снимковые тесты не реализуют параллельный рендерер:

1. `render_fixture` в `tests/conftest.py` копирует симулированные
   `raw_entries.json` фикстуры, необязательный `raw_blocks.json` и `thread.json` во
   временную директорию.
2. Он вызывает `pplx_export.commands.rerender_cmd.rerender`, ту же функцию,
   которая используется `pplx-export re-render`.
3. Фабрика фикстур `rendered` возвращает свежий вывод и зафиксированную
   директорию `golden/` фикстуры.
4. Тесты сравнивают `conversation.md` и каждый `turns/turn_*.md` побайтово.

Инварианты содержимого дополняют побайтовое равенство: ответы не должны сворачиваться в пустой
заполнитель `(无)`, а остатки представления словаря, такие как `{'type': ...`, не должны
просачиваться в отображаемый текст.

<a id="adding-a-test" data-pplx-source-anchor="true"></a>
## Добавление теста

- **Существующая логика** — добавьте тест в соответствующий тематический модуль. Используйте
  `tmp_path`, заглушки и `monkeypatch`; никогда не обращайтесь к сети или реальному
  `~/.config`.
- **Регрессия ошибки** — предпочитайте соответствующий тематический модуль. Создайте
  модуль `test_fix_<lineage>_<slug>.py`, когда сохранение происхождения рецензии существенно
  улучшает прослеживаемость; не предполагайте один модуль на одно замечание.
- **Регрессия рендеринга** — добавьте или сократите симулированную фикстуру, перегенерируйте ее
  эталонные продукты с помощью инструмента обслуживания, затем зарегистрируйте ее в
  `test_render_snapshots.py` или добавьте утверждения для конкретного сценария.

Следуйте стилю соседних модулей: аннотации типов,
`from __future__ import annotations` и двуязычные строки документации модулей.
